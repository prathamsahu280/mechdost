# 13 · RBAC, security & abuse protection

Status: decided · Phase 1 · Decisions: Staff security, Non-functional requirements; research `../research/security-vulnerabilities.md` (recent CVEs, written after research completes)

## RBAC

- Permissions are `resource:action` strings (orders:read, orders:route, orders:refund, refunds:approve, products:publish, partners:approve, content:publish, settings:write, customers:impersonate, …) stored in `permissions`; roles in `roles` with `role_permissions`; `user_roles` with optional `city_id` and `partner_id` scope. Firebase custom claims carry role ids + partner_id; the API resolves effective permissions per request (per-instance cache 60 s keyed by the sign-in time, so every new sign-in loads fresh; invalidated locally on change).
- Default roles and matrix: see `../research/ecommerce-baseline.md` §7 (super_admin, ops_manager, support_agent, finance, catalogue_manager, city_manager, marketing, seller_owner, seller_staff, workshop_owner, workshop_staff, mechanic, customer, guest).
- Enforcement: Hono middleware `requirePermission()` + repository-level scoping (`actor`), RLS mirror in Supabase (defence in depth); live pings in Firebase RTDB carry opaque ids only and each user can read only `/inbox/{uid}` (rule `auth.uid === $uid`), the worker decides recipients from Postgres, data always refetched through the API; UI hides what the actor cannot do; 404 for cross-tenant ids.
- Four-eyes: refunds/manual coin grants/payouts/commission changes above `settings.approval_threshold_paise` require requester ≠ approver.
- Staff 2FA (TOTP) implemented; enforced automatically once any staff beyond founders exists (`settings.enforce_staff_2fa` auto-true on 2nd staff).
- **CSP (2026-11-09):** site-wide allow-list policy from `apps/web/src/lib/csp.ts` (decisions 2026-11-09); and in real sign-in mode a nonce + `strict-dynamic` policy on `/login` (proxy `src/proxy.ts`, layout inline scripts by hash).
- Staff sign-in = password + a phone code every time (decision 2026-11-01); the API grants staff permissions only to a session made by both steps (`staff_2fa` custom-token claim, ≤ 12 h old), otherwise `STAFF_2FA_REQUIRED` (built 2026-11-09, spec 01).
- Sessions: staff idle 30 min / absolute 12 h; partners 7 days; customers 30 days; sign-out-all; new-device alert (P1).
- Audit log on every mutation (actor, ip, entity, before/after, reason) — immutable.

## Encryption (decision 2026-11-01, user: "the passwords and database need to be properly encrypted")

| Layer       | What                                                                                                                                                                                                                                     | Where                       |
| ----------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | --------------------------- |
| Passwords   | Never stored by us; Firebase Auth hashes them (scrypt). Demo: PBKDF2-SHA-256 + salt.                                                                                                                                                     | spec 01                     |
| In transit  | TLS on every non-local DB connection (`tlsFor`): verify-full with `DATABASE_CA_CERT`, **mandatory in production** (the API refuses to start without it, so no MITM downgrade); dev may use `require` until Q23; HTTPS + HSTS for web/API | `packages/db/src/client.ts` |
| At rest     | Supabase AES-256 disk + backup encryption; PITR backups encrypted                                                                                                                                                                        | Supabase                    |
| Field level | AES-256-GCM envelope `v1.<keyId>.<iv>.<ct>.<tag>`, column name as AAD, random IV; blind index (HMAC-SHA-256) for lookups                                                                                                                 | `packages/db/src/crypto.ts` |
| DB guard    | CHECK constraints: `*_enc` columns accept only envelopes → plain text is rejected by Postgres (23514)                                                                                                                                    | migrations 0004–0005        |

Encrypted columns: `shops.pan_enc` (+ unique `pan_index`), `partner_applications.kyc_enc` (PAN, GSTIN, bank/UPI for payouts as JSON), `refunds.destination_enc` (required when `mode = 'bank_upi'`), `staff_security.totp_secret_enc`. Any new column holding government IDs, bank/UPI details, documents' numbers or secrets **must** be `*_enc` + `encryptedCheck` (checklist item). Keys: `DATA_ENCRYPTION_KEYS` (`id:base64,…`), `DATA_ENCRYPTION_KEY_ID`, `DATA_INDEX_KEY` — Secret Manager in production, never in git; rotation = add a key id, switch the current id, re-encrypt with `needsRotation` in a job, then retire the old key. Plain (for lookups): phone, email, names, addresses — protected by RLS, least privilege, PII masking for support, audit logs that record field names only. Tests: `packages/db/test/crypto.test.ts` (round trip, tamper, wrong column, rotation, config), `integrity.test.ts` "encryption at the database boundary", `tls.test.ts`.

**Logging (2026-11-03):** error logs carry `safeError(err)` only (error class, Postgres SQLSTATE, stack frames) plus ids and codes; never `err.message`/`err.stack`, which for database errors contain the query parameters (phones, message text). Jobs count failures outside the failed transaction and park poison items after 5 attempts with an error code.

## Seller onboarding (2026-11-13)

- **Permissions:** `prices:approve` (new, in the ops roles) decides price requests; `partners:approve` approves or rejects applications and creates invites; `partners:write` lists and revokes invites; `content:write` publishes agreement versions. Shop routes need the shop's owner or staff (another shop → 404).
- **Abuse:** the public application and invite routes need Turnstile; 5 applications and 30 invite opens per IP per hour, and 3 applications per mobile number per day (keyed by a hash of the number); the location search allows 10 searches a minute per client and never searches as you type (Nominatim policy).
- **Invite tokens:** only a SHA-256 hash is stored; the token travels encrypted in the outbox payload (`tokenEnc`) until the email is sent; single use, expiring, per city; never written to analytics (`redactPath`).
- **KYC:** the GSTIN or enrolment number is stored in `partner_applications.kyc_enc` with a `gstin_index` blind index for duplicate checks; the shop owner is linked once (`owner_user_id`).

## Permission `prices:write` (2026-11-13, Q26)

"Set customer prices per city and PIN code": super_admin, ops_manager and finance. Not catalogue_manager (catalogue texts only) and not city_manager until prices are city-scoped. The price board (`GET /v1/admin/prices/products/{slug}`) needs it too (one permission per area: whoever sees the margins can set them). Writes are compare-and-set on `version` (`STALE_PRICE`) and audited (`price.set` / `price.cleared` with before/after).

## Staff roles from the console, masking and audit viewing (2026-11-15)

- No new permission: `staff:manage` (super admin), `customers:read` / `customers:read_pii` (the design called it `customers:pii`; the existing key is reused), `audit:read` (super admin, finance). All three screens also need an all-cities grant (`SCOPE_REQUIRED` otherwise) because staff, customers and the audit log have no city. `pnpm db:seed` is not needed for this change.
- Rules enforced in the repository, not only the UI: no self role changes; `super_admin` and `finance` only by a super admin; the last super admin stays; reasons are mandatory; every change is audited with the reason and emits an analytics event.
- Masking: phone `••••••` plus the last 4 digits, email first letter plus domain, for everyone in lists and for roles without `customers:read_pii` in the customer view. An unmasked customer view writes `customer.pii_viewed` (actor, customer, time; no contact data in the row). The audit log viewer never unmasks: its `before`/`after` are redacted for all roles (`redactAuditJson`).
- Rate limits: search and audit queries 30 per minute per user (`adminSearch`) on top of the per-user API limit; all strict Zod bodies and query strings (unknown fields 400).
- Sessions: a role change drops the person's cached session on the handling instance; removing a role also revokes their Firebase refresh tokens; other instances converge within the 60 s session cache. Staff sign-in completion is recorded (`auth.staff_signed_in`) for the "last sign-in" column.
- Tests: `packages/db/test/staff-admin.test.ts`, `customer-search.test.ts`, `audit-viewer.test.ts`, `apps/api/test/admin-people.test.ts` (401 / 403 / `SCOPE_REQUIRED` / `STAFF_2FA_REQUIRED` matrix on every route, foreign ids 404, strict bodies, rate limit, session refresh at once).

## CSV exports (2026-11-15)

- **New permission `exports:run`** (super admin through "all", ops manager, city manager, finance). **`pnpm db:seed` is needed** on the live database to add it to `permissions` and `role_permissions` (idempotent catalogue sync); until it runs, the permission does not exist in the database and the export routes answer 403 for everyone, super admin included. Each dataset also needs its own read permission (orders and sub-orders `orders:read`, refunds `refunds:read`, service requests `service:read`, partners `partners:read`, customers `customers:read`); customers need an all-cities grant (`SCOPE_REQUIRED`); a city-scoped staff member exports only their cities (the narrower of the `exports:run` and dataset scopes; another city is 404).
- **Contact masking:** the customers file masks phone and email unless the viewer holds `customers:read_pii` in an all-cities grant; the audit row records `masked`. No bank, UPI, address or note columns exist in any export.
- **Download link:** `base64url(payload).base64url(HMAC-SHA256)` with the payload `{user, dataset, from, to, city, expiry, nonce}`, key derived from the data keyring's index key, valid 600 seconds, only for the staff member it was issued to (user mismatch is `EXPORT_LINK_INVALID`, expiry `EXPORT_LINK_EXPIRED`). The route still authenticates, re-checks permissions and scope on every download; a link grants nothing by itself. It is replayable by the same person inside the 10 minutes (each download is audited).
- **Abuse limits:** 40 export calls an hour per staff user (request and download each count), 180 days and 50,000 rows per file, keyset reads on indexed time columns, CSV formula neutralising. Role-leak matrix: `apps/api/test/admin-exports.test.ts`.

## Uploads (job photos, 2026-11-15)

Rules the one upload pipeline (`apps/api/src/photos/`) enforces; product photos reuse it next tier.

- **Streamed size limit:** 8 MB (+64 KB multipart framing) on the upload route only; the global 1 MB body limit skips exactly that route. A larger file is 413 `PHOTO_TOO_LARGE` before anything is decoded. A 50-megapixel decode cap (`limitInputPixels`) guards decompression bombs; at most 2 pictures are decoded at once per instance.
- **Type by bytes, never by name or MIME:** JPEG, PNG and WebP only (the decoder's format must equal the header's). SVG, GIF, AVIF, TIFF, PDF and text are 422 `PHOTO_TYPE`. **HEIC** (HEVC) is refused with 422 `PHOTO_HEIC` ("Please upload JPG or PNG"): the libvips bundled with sharp 0.35.5 decodes AVIF but has no HEVC decoder (checked 2026-11-15); iOS converts to JPEG for `accept="image/jpeg,…"` file inputs.
- **Re-encode, never store the original:** auto-rotate from EXIF orientation, then WebP at 1600 px and 480 px. All metadata (GPS, camera, owner, trailing payloads) is gone; a test checks the output has no EXIF.
- **Random object keys** (`job/{requestId}/{uuid}.webp`), enforced by a CHECK constraint; the file name is never used. No path traversal is possible because no client string reaches a storage path.
- **Rights on every read:** listings are scoped (own workshop, own customer, city staff; foreign ids 404); images need a signed 10-minute URL or the public rule. Private bucket; the Storage secret key is server-only and never in a URL, log or error.
- **Rate limit:** 30 uploads per 10 minutes per workshop user; image reads 600/min per IP; gallery 120/min per IP; the normal per-user and per-IP limits apply too.
- **Audit:** add and remove each write `audit_log` (removal keeps the before row) and a server event; delete is a soft delete.
- **Dependencies:** `sharp` 0.35.5 (released 2026-09-27, above the 0.35.4 advisory floor, older than the 3-day release-age policy); `allowBuilds` already lists sharp.

## Shop team and money visibility (2026-11-15)

Owner-only routes for the busy toggle and the team check the caller's own `seller_owner` grant for the shop id (404 for any other shop, 403 `OWNER_ONLY` for staff of that shop, 403 for everyone else, 401 anonymous). Staff invites are bound to a phone that is proved by the sign-in code, never by a link, and grant nothing until the invitee accepts them (consent; accept and decline are invitee-only, 404 for any other person or an unverified phone, single use, compare-and-set on the invite version). MechDost staff accounts cannot accept (one person, one side). The owner sees the name they typed, never the account name. Removing a member revokes the role in the same transaction and drops their cached session. `payoutPaise` and the shop's own line prices are returned only for shops where the caller holds `payouts:read` (owners, not staff). Rate limit on invites: 20 an hour per user. Role-leak matrix: `apps/api/test/shop-team.test.ts`.

## Support attachments and payout details (2026-11-15)

- Support photos reuse the job-photo pipeline unchanged (magic bytes, HEIC refused, 50 MP cap, EXIF removed by re-encode, random keys `ticket/{uuid}/{uuid}.webp`, private bucket). Up to 4 per message, 8 MB each, the multipart routes have their own body limit (4 x 8 MB + framing; the global 1 MB limit skips exactly `/v1/support/threads` and `/v1/support/tickets/{code}/photo-messages`). Rights are checked before image work (customer: own request only, 404 otherwise; closed request 409). Reads need the 10-minute signed URL; anything else is 404. Rate limits: threads 20 an hour, photo uploads 20 per 10 minutes, payout destination 10 an hour per customer, images 600 a minute per IP.
- A customer's UPI id or bank details are encrypted with the data keyring (AAD `support_tickets.refund_destination_enc`), returned and audited only as a mask or a kind, never logged, and copied under the refund's own AAD when staff request the refund. The refund request from a ticket needs `tickets:reply` and `refunds:initiate`; the full value is shown only to the approver of an approved refund (existing audited reveal).
- Role-leak matrix: `apps/api/test/support-threads.test.ts` (anonymous 401, customer and marketing 403 on the staff refund route, foreign customer 404 on threads, destinations and photos, staff are not thread owners).

### Support inbox, guest tickets, deletion (2026-11-15)

- Guest ticket routes (`/v1/support-guest/*`) are public: Turnstile on creation, limits per IP, per phone and per reference (key guessing), strict bodies, key stored as SHA-256 and compared in constant time, identical 404 for wrong key / unknown reference, nothing sent to guest-typed contact details.
- `tickets:assign` is evaluated for the request's own city; agents with only `tickets:reply` can take a free request or release their own. Canned replies are global: editing needs a platform-wide `content:write` grant. Deletion confirmation needs `customers:block`.

## Catalogue tier 2 (2026-11-15)

No new permission (no `db:seed`). Recommendation rules: `categories:write`; PIN waitlist demand: `cities:manage` with city scope; Privacy and notify-me: `account:read` / `account:write` plus the session user id (a foreign export id is 404). The data download is a private authenticated route, never a public URL, and never cached.

## Uploads: product photos (2026-11-15)

Same image gate as job photos (spec 06). Differences: staff (`products:write`) and shops (`inventory:write`, own products, setting on) upload; 40 uploads per 10 minutes per user; the result is public once approved, through a cacheable API route by id (never a Storage URL or key); a pending, refused or removed photo is 404 unless the URL has a valid 10-minute HMAC from a rights-checked listing. Approval and refusal need `products:publish`. The approval queue, descriptions and shop names are staff-only data. Role-leak tests: `apps/api/test/product-photos.test.ts`.
